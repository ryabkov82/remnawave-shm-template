# Дополнительный трафик VFF — шаблон `remnawave_traffic_addon`

Шаблон выполняется только на `CREATE` услуги «Дополнительный трафик 300 ГБ». Он поднимает лимит уже существующего пользователя Remnawave `us_<parent_user_service_id>`. Пользователя панели он не создаёт и не удаляет, срок, расход, стратегию и параметры подключения не меняет.

Основной шаблон `templates/shm-remnawave.template.sh` этим этапом не изменяется. Пока он при `ACTIVATE` и `PROLONGATE` записывает каталожный лимит, включение продажи в Production заблокировано. См. раздел «Блокирующие условия».

Живой рендер `us.service.settings.traffic_addon` на экземпляре услуги 17 не выполнялся: экземпляров нет, создавать их на этом этапе нельзя. Путь совпадает с уже используемым `us.service.settings.remnawave.*`.

## 2. Контракт входных данных

### Каталог

`us.service.settings.traffic_addon` должен описывать поддерживаемую модель: бренд `vff`, родительская категория `vpn-mz-test`, непустой список `parent_service_ids`, положительный `bytes`, стратегия `MONTH`, период `remnawave_monthly_reset`, cron `20 0 1 * *`, часовой пояс `UTC`, `max_purchases_per_period` = 1. Иначе постоянный отказ `unsupported_catalog`.

Экземпляр обязан быть услугой 17 категории `traffic-add-vff`. Поле `bytes` каталога проверяется по форме, но в PATCH не подставляется.

### Экземпляр

`us.settings`:

```json
{
  "purchase_id": "0123456789abcdef0123456789abcdef",
  "parent_user_service_id": 18432,
  "period": "2026-11"
}
```

`purchase_id` — 32 шестнадцатеричных символа в нижнем регистре. `period` — `YYYY-MM` цикла, который открывается 1-го числа в 00:20:00 UTC. Отсутствие или неверный формат даёт постоянный отказ до любого запроса в Remnawave.

### Storage

Ключ `ta-<parent_user_service_id>-<YYYYMM>`, не длиннее 32 символов. Тело создаёт vpnbot до заказа. Шаблон ключ не создаёт: отсутствие записи — постоянный `storage_missing`.

`user_service_id` хранится внутри JSON. Колонку storage `user_service_id` шаблон не передаёт: `REMOVED` удаляет строки storage по этой колонке.

Обязательные поля снимка: `purchase_id`, `user_id`, `parent_user_service_id`, `period`, `period_starts_at`, `period_ends_at`, `expected_amount`, `base_limit_bytes`, `addon_bytes`, `applied_limit_bytes`, `state`, `snapshot_mac`. Границы периода должны быть ровно `YYYY-MM-01T00:20:00Z` и то же время следующего месяца.

`expected_amount` — строка с двумя знаками, например `"150.00"`. vpnbot записывает её при резервировании, до отправки заказа. Пустое или отсутствующее значение — постоянный `expected_amount_missing`. Шаблон стоимость из каталога в проверку оплаты не подставляет.

Объёмы — положительные целые, не больше 9007199254740991, чтобы `jq` не потерял точность. Итог фиксируется при покупке:

`applied_limit_bytes = base_limit_bytes + addon_bytes`

Для текущих тарифов это 322122547200 + 322122547200 = 644245094400. Позднее изменение каталога эту тройку не переписывает. Равенства базы и пакета итогу недостаточно: снимок ещё должен нести верный `snapshot_mac`.

Неизменяемые поля после первой успешной проверки контракта: `purchase_id`, `user_id`, `parent_user_service_id`, `period`, обе границы, `expected_amount`, `base_limit_bytes`, `addon_bytes`, `applied_limit_bytes`. Одна функция проверяет типы, диапазоны, сумму и подпись при первом чтении, после получения блокировки и перед записью состояния. Изменённый снимок без совпадения с уже принятым каноническим видом не используется.

`snapshot_mac` — HMAC-SHA256 в нижнем hex. Ключ берётся из `server.settings.traffic_addon.snapshot_key` и в storage не хранится. Каноническая строка — компактный JSON с полями в таком порядке: `purchase_id`, `user_id`, `parent_user_service_id`, `period`, `period_starts_at`, `period_ends_at`, `expected_amount`, `base_limit_bytes`, `addon_bytes`, `applied_limit_bytes`. Нет ключа — постоянный `snapshot_key_missing`. Нет или неверна подпись — постоянный `snapshot_mismatch`.

Шаблон добавляет служебные поля:

- `version` — счётчик записей, не CAS;
- `write_id` — случайный идентификатор конкретной записи; после POST шаблон читает запись и сравнивает полное нормализованное JSON с отправленным телом;
- `apply_proof` — снимок перед PATCH: `remnawave_uuid`, `expire_at`, `strategy`, `observed_limit_before`, затем `phase` (`patching` или `confirmed`) и `observed_limit_after`, равный подтверждённому лимиту;
- `amount` — фактически списанная сумма с двумя знаками;
- `withdraw_id` и `user_service_id` — только если в снимке их ещё не было.

Состояния, которые шаблон понимает: `RESERVED`, `ORDER_UNKNOWN`, `PAID`, `APPLIED`, `EXPIRED`, `REFUNDED`, `FAILED`.

Сравнение полного тела и `write_id` не является CAS. Запись, которая произойдёт после подтверждающего чтения, шаблон не увидит.

### Списание

Оплату подтверждает объект `us.withdraw.get`, а не поле `state`. Нужны непустой `withdraw_date`, `user_service_id` этого экземпляра, `user_id` владельца, `service_id` 17 и положительный числовой `withdraw_id`. Сумма `total` в копейках должна совпасть с `expected_amount`. Если `amount` уже записан, он тоже должен совпасть с `total`; пустой `amount` заполняется из списания и только этой суммой.

Уже записанные `withdraw_id` и `user_service_id` заменять нельзя. Другой `withdraw_id` — постоянный `withdraw_mismatch`. Другой `user_service_id` — постоянный `user_service_mismatch`. Другая сумма — постоянный `amount_mismatch`.

Почему шаблон сам переводит `RESERVED` и `ORDER_UNKNOWN` в `PAID`: `CREATE` может начаться раньше, чем vpnbot успеет записать оплату. Ждать эту запись означало бы зависеть от второго писателя. Неоплаченное списание — временный `payment_not_confirmed`, spool повторяет задачу. Наличия ключа или состояния `RESERVED` недостаточно для PATCH.

Шаблон не создаёт заказ, не списывает деньги и не делает возврат.

## 3. Алгоритм

1. Событие не `CREATE` — постоянный `unexpected_event`.
2. Проверить услугу, категорию, каталог и параметры экземпляра.
3. Прочитать storage. Терминальные `EXPIRED`, `REFUNDED` и `FAILED` не реактивируются.
4. Сверить окно периода со свежим временем, а не с часами начала запуска. `now >= period_ends_at` — постоянный `period_closed`. `now < period_starts_at` — временный `period_not_open`. То же чтение часов повторяется после блокировки, непосредственно перед PATCH, после PATCH и перед записью `APPLIED`.
5. Сверить списание. При оплаченном `RESERVED` или `ORDER_UNKNOWN` локально подготовить переход в `PAID`.
6. Прочитать родительскую услугу сессией владельца: `GET /shm/v1/user/service?user_service_id=<parent>`. Пустой список или чужой `user_id` — `parent_not_owned`. Статус не `ACTIVE` — `parent_not_active`. Чужая категория — `parent_category_mismatch`. Тариф вне `parent_service_ids` — `tariff_not_allowed`. Так отсекаются VFF Premium (услуга 14) и Friends Connect.
7. Взять ключ `tl-<parent_user_service_id>` на 120 секунд. В записи есть `lock_id` этого запуска, `purchase_id`, имя обработчика и `until`. Только подтверждённое HTTP 404 означает отсутствие записи. Timeout, HTTP 5xx, 401, 403, прочий код и неразборчивый JSON дают временный `lock_unavailable`: блокировку нельзя ни создать заново, ни перезаписать. HTTP 400 или 409 у начального PUT означает, что ключ уже есть; следующий GET обязан быть успешным, иначе это тоже `lock_unavailable`. Чужой непросроченный `lock_id` даёт временный `lock_held`. Это не взаимное исключение: см. раздел о блокировке.
8. Ещё раз прочитать покупку, проверить контракт и отклонить терминальное состояние.
9. Прочитать `GET /api/users/by-username/us_<parent>`. Имя должно совпасть. Стратегия должна быть `MONTH`. Статусы `ACTIVE` и `LIMITED` допустимы. `DISABLED` и `EXPIRED` дают `panel_status`; отдельный enable не вызывается. `expireAt` должен разбираться и быть в будущем. Пустая или неверная дата — постоянный `expire_invalid`. Дата в прошлом при статусе `ACTIVE` — постоянный `subscription_expired`.
10. Открыть период по правилу из раздела «Даты Remnawave» и по часам этого шага. Сброс трафика шаблон не вызывает.
11. Если лимит уже равен `applied_limit_bytes`, UUID совпадает и `apply_proof.phase` равен `patching` или `confirmed`, повторный PATCH не делается: запись переводится в `APPLIED`.
12. Если лимит не равен ни базе, ни этому подтверждённому итогу — постоянный `limit_conflict`. Чужое значение не перезаписывается.
13. Если лимит равен базе, ещё раз прочитать родителя и панель, проверить будущий `expireAt` и свежий период, записать `apply_proof` с `phase=patching`, снова проверить период и свой `lock_id` и только потом выполнить PATCH. Закрытый период на этом шаге — постоянный `period_closed`, PATCH не отправляется. Потеря своего lock до PATCH — временный `lock_lost`, лимит не меняется.
14. Тело PATCH содержит только `uuid` и `trafficLimitBytes`, равный сохранённому `applied_limit_bytes`. Срок, стратегия, расход и параметры подключения не отправляются. Не используется формула «текущий лимит + пакет».
15. После PATCH пользователь читается снова. Если свежие часы уже не раньше `period_ends_at`, а лимит стал равен итогу, состояние `APPLIED` не ставится: в записи остаётся прежнее состояние, `last_error=period_crossed_after_patch`, `phase=patching`, выход — постоянный `period_crossed`. Пакет прошлого периода не отмечается как выданный в новом.
16. Перед записью `APPLIED` шаблон заново проверяет свой lock, читает storage, проверяет контракт и допустимый переход. `EXPIRED`, `FAILED` и `REFUNDED` устаревшая операция не восстанавливает. Если lock к этому моменту потерян, выход временный `lock_lost`, `APPLIED` не пишется.
17. UUID, имя и стратегия должны совпасть со снимком, лимит — с сохранённым итогом. Новый `expireAt` в будущем не отменяет уже выполненный PATCH: это может быть штатное продление родителя. Шаблон срок не отправляет, записывает наблюдаемый `expireAt` в доказательство и завершает `APPLIED`. Неразборчивый или прошедший новый срок оставляет состояние `PAID`, ставит `last_error=parent_expire_changed` и выходит временно: панель уже изменена, сверка должна разобрать запись.
18. `observed_limit_after` записывается один раз и равен лимиту подтверждающего чтения. Код 0 возвращается после записи `APPLIED`.
19. Если ответ PATCH потерян, повторное чтение видит итог и доказательство `patching` и завершает операцию без второго увеличения.
20. Если состояние уже `APPLIED`, доказательство подтверждено, а лимит снова стал равен базе, шаблон возвращает сохранённый итог. Это ремонт после затирания лимита продлением. Гонку с продлением он не закрывает. Повторные проверки не заменяют атомарную блокировку.

Код 0 возвращается только вместе со строкой `RESULT level=ok reason=applied` и после повторного чтения панели. Любой отказ — код 1 и `RESULT level=temporary|permanent reason=...` в stderr. Stderr выбран потому, что часть проверок вызывается из `$(...)`: сообщение в stdout такой вызов потерял бы.

## 4. Ошибки

Временные, spool может повторять: недоступность SHM, Remnawave, storage или чтения блокировки, timeout, HTTP 5xx, 401 и 403 блокировки, 408, 429, потеря ответа, конфликт полного тела записи, занятый или потерянный lock, период ещё не начался, сброс периода не подтверждён, списание ещё не оплачено, срок родителя стал непригоден уже после PATCH.

Постоянные, для административного разбора: неверные параметры, неподдерживаемый каталог, отсутствие ключа подписи, неверная подпись, пустой `expected_amount`, чужая или неактивная подписка, тариф вне списка, закрытый период, пересечение границы после PATCH, несовпадение суммы, подмена `withdraw_id` или `user_service_id`, конфликт лимита, отсутствие или прошедший `expireAt`, отсутствие пользователя панели, терминальное состояние, отсутствие записи storage, изменённый неизменяемый снимок, изменённая стратегия после PATCH.

`FAILED` бесконечно повторяющийся `CREATE` не переводит обратно в работу. Восстановление — отдельное действие сверки: она возвращает состояние в `PAID` и возобновляет задачу. До появления сверки постоянный `FAIL` тоже повторяется, потому что у `retry_task` нет предела. Это блокирует Production.

Ручной `success` задачи SHM не использовать: он переведёт услугу в `ACTIVE`, даже если лимит не менялся. Возврат из шаблона не выполняется.

## 5. Контракт vpnbot и фоновой сверки

vpnbot до заказа делает `Storage::add` ключа `ta-<parent>-<YYYYMM>` без колонки `user_service_id`. Повторный add отклоняет вторую покупку за период. В заказ передаются `purchase_id`, `parent_user_service_id` и `period`. Поля `months` и `cost` не передаются.

До отправки заказа vpnbot записывает и подписывает снимок: границы периода, `expected_amount`, базу, пакет и итог. Ключ HMAC лежит в `server.settings.traffic_addon.snapshot_key` на сервере группы 6, в той же зоне доверия, что токен Remnawave. Пользовательский storage этот ключ не содержит. Пока vpnbot подпись не пишет, шаблон закрывается `snapshot_key_missing` или `snapshot_mismatch`, и продажу включать нельзя.

`amount` — фактически списанная сумма. Шаблон сам заполняет пустые `amount`, `withdraw_id` и `user_service_id` из подтверждённого списания и не заменяет уже записанные значения. Он не ждёт, что vpnbot успеет поставить `PAID`. Оплаченное `RESERVED` и `ORDER_UNKNOWN` он проводит сам. Неоплаченный заказ остаётся временной ошибкой; vpnbot не должен снимать резерв по одному неудачному поиску.

Сверка, которой ещё нет, должна:

- читать `RESULT level=permanent` и ставить задаче `POST /admin/spool/manual/pause`, а не `success`;
- временные ошибки не останавливать;
- не реактивировать `EXPIRED`, `FAILED` и `REFUNDED` из устаревшей операции;
- `FAILED` переводить в `PAID` только явным административным восстановлением;
- при `period_crossed` и `last_error=period_crossed_after_patch` не считать пакет выданным в новом периоде: фаза ещё `patching`, состояние не `APPLIED`, лимит панели равен итогу прошлого окна;
- понижать лимит до `base_limit_bytes` только когда текущий лимит равен сохранённому итогу и `lastTrafficResetAt` не раньше `period_ends_at` того окна;
- если после `period_crossed` лимит всё ещё равен базе, PATCH не применился: пакет не выдавать и повторно не списывать;
- поздний `CREATE`, который начинается уже с `period_closed`, не должен делать новый PATCH;
- `parent_expire_changed` после успешного PATCH не считать отказом в лимите: срок шаблон не менял, сверка сверяет наблюдаемый `expireAt` и сохранённый итог;
- не вызывать reset-traffic и не понижать лимит только потому, что наступило 00:20 UTC;
- не затирать лимит, который не равен ни базе, ни сохранённому итогу;
- проверять `snapshot_mac` тем же ключом и не доверять снимку с подменёнными объёмом, итогом, суммой или финансовыми идентификаторами.

Общий протокол писателей — один ключ `tl-<parent_user_service_id>` без месяца. Его должны использовать шаблон, будущая сверка и будущие правки `ACTIVATE` / `PROLONGATE` / `BLOCK`. `version` и `write_id` показывают, совпало ли полное тело с немедленным повторным чтением. Ни TTL, ни `version`, ни `write_id` гонку не устраняют. Подробности — в разделе о блокировке.

## 6. Доказательство применения

Точная последовательность записи:

1. Прочитать пользователя. Лимит равен сохранённой базе, статус `ACTIVE` или `LIMITED`, `expireAt` в будущем. Родительская услуга SHM перечитывается непосредственно перед этим шагом.
2. Проверить свежий период и что lock всё ещё наш и не истёк.
3. Записать в ту же запись покупки `apply_proof`: `phase=patching`, `remnawave_uuid`, `expire_at`, `strategy`, `observed_limit_before`. Состояние покупки на этом шаге ещё не `APPLIED`.
4. Снова прочитать часы и lock. Закрытый период — `period_closed` без PATCH. Чужой или истёкший lock — `lock_lost` без PATCH.
5. Отправить PATCH только с `uuid` и абсолютным `trafficLimitBytes`.
6. Прочитать пользователя ещё раз и снова прочитать часы.
7. Если граница периода пересечена, а лимит уже итоговый, записать `last_error=period_crossed_after_patch` и не ставить `APPLIED`.
8. Перечитать storage и lock. Терминальное состояние не восстанавливать. Считать пакет предоставленным, только если UUID, имя и стратегия совпали, лимит равен сохранённому итогу, а `expireAt` всё ещё в будущем. Изменившийся, но будущий срок записывается как наблюдение и не отменяет выдачу.
9. Одной записью поставить `state=APPLIED`, `apply_proof.phase=confirmed`, `observed_limit_after` равным подтверждённому лимиту и наблюдаемый `expire_at`. Код 0 возвращается после этой записи.

Аварийные точки:

| Обрыв | Что остаётся | Повтор |
|---|---|---|
| До записи `apply_proof` | лимит равен базе, доказательства нет | один PATCH |
| После `apply_proof`, до отправки PATCH | `phase=patching`, лимит равен базе | один PATCH |
| PATCH отправлен, панель лимит не сменила | `phase=patching`, лимит равен базе | один PATCH |
| PATCH выполнен, HTTP-ответ потерян, повторное чтение уже показывает итог | тот же запуск дописывает `APPLIED` | второго PATCH нет |
| PATCH выполнен, подтверждающий GET не удался | `phase=patching`, лимит уже итоговый | без второго PATCH, затем `APPLIED` |
| Подтверждающий GET успешен, запись `APPLIED` не удалась | `phase=patching`, лимит итоговый | без второго PATCH, затем `APPLIED` |
| До PATCH часы пересекли границу периода | `phase=patching`, лимит равен базе | PATCH не отправлять; поздний повтор получает `period_closed` |
| Во время PATCH часы пересекли границу, лимит уже итоговый | `phase=patching`, `last_error=period_crossed_after_patch`, состояние не `APPLIED` | сверка не выдаёт пакет в новом периоде и снижает лимит только после подтверждённого сброса |
| После PATCH storage стал `EXPIRED`, `FAILED` или `REFUNDED` | терминальное состояние сохраняется, лимит уже изменён | `APPLIED` не писать; сверка разбирает панель отдельно |
| После PATCH `expireAt` сменился на будущую дату | лимит итоговый, в доказательстве новый срок | `APPLIED`, срок шаблон не отправлял |

Ручная установка итогового лимита без `apply_proof` этого UUID и фазы `patching` или `confirmed` — постоянный `limit_conflict`. Успехом она не считается.

Остаточный зазор: после записи `phase=patching` и до подтверждающего GET администратор может выставить тот же итог. Повтор примет его за свой PATCH. Условной записи в панели нет, поэтому окно не закрывается.

## 6.1. Даты Remnawave 3.4.8

В схеме Users `createdAt` обязателен и по умолчанию равен `now()`. `lastTrafficResetAt` — nullable. Создание пользователя копирует `lastTrafficResetAt` из запроса; основной шаблон это поле не передаёт, поэтому у новой подписки оно пустое, а расход начинается с нуля.

Плановый сброс стратегии `MONTH` выбирает пользователей с этой стратегией и статусом не `LIMITED` (отдельный проход — для `LIMITED`). Фильтра по `createdAt` у `MONTH` нет: пользователь, созданный в текущем окне, попадёт в ближайший запуск `20 0 1 * *` UTC. Сброс пишет `lastTrafficResetAt`, обнуляет расход и не меняет `trafficLimitBytes`. Шаблон этот механизм не вызывает.

Период покупки открыт, когда текущее время внутри его границ и выполнено одно из условий:

- `lastTrafficResetAt` разобран, не позже текущего времени и не раньше `period_starts_at`;
- `lastTrafficResetAt` пуст, а `createdAt` разобран, не в будущем и не раньше `period_starts_at`.

Иначе временный `period_not_confirmed`. `createdAt` в будущем — временный `created_at_in_future`, даже если отметка сброса уже есть: будущая дата не доказывает, что счётчик относится к этому окну.

Поэтому покупка доступна подписке, созданной в текущем периоде и ещё не прошедшей плановый сброс. Подписка прошлого периода без сброса в текущем окне, в том числе если панель была недоступна в `00:20` UTC, пакет не получает. Пустые обе даты тоже не открывают период.

## 6.2. Блокировка

Ключ `tl-<parent_user_service_id>` намеренно без месяца. Иначе покупка старого периода и сверка нового периода пишут лимит одновременно. Один ключ на подписку — рекомендуемый общий порядок для addon CREATE, будущего `ACTIVATE` / `PROLONGATE` / `BLOCK` и сверки.

Тело: `lock_id` (случайные 32 hex этого запуска), `purchase_id`, `handler`, `parent_user_service_id`, `until`. Владелец — `lock_id`, не `purchase_id`: два одновременных CREATE одной покупки не должны оба войти. Освобождение удаляет ключ только если прочитанный `lock_id` всё ещё наш. Чужой ключ не удаляется.

Это не устраняет конкурентный доступ.

- Только HTTP 404 — отсутствие блокировки. Ошибка чтения не даёт права создать или заменить ключ. Ошибка начального PUT, кроме 400 и 409, тоже не означает, что ключ уже существует.
- TTL может истечь во время PATCH. Перед записью доказательства и перед PATCH свой lock проверяется снова; истёкший или чужой lock отменяет PATCH. Если PATCH уже ушёл, а lock потерян до записи `APPLIED`, шаблон не ставит `APPLIED`. Панель при этом уже может быть изменена, и второй обработчик в этом окне может писать лимит параллельно.
- Между чтением «это наш lock» и `DELETE` другой обработчик успевает заменить ключ. `DELETE` в SHM безусловный, поэтому чужой lock всё ещё можно снести. Отсутствие CAS это не лечит.
- Просроченный lock перезаписывается через `POST` и затем читается. Два таких перехвата проходят оба, если оба увидели истечение до записи другого.
- `version` и `write_id` увеличиваются локально. После POST сравнивается полное нормализованное тело с немедленным чтением. Расхождение — временный `storage_conflict`. Запись после этого чтения не обнаруживается. Это не compare-and-swap.
- На границе периода один ключ сериализует попытки только пока все обработчики его соблюдают. Основной шаблон его пока не берёт, поэтому продление по-прежнему затирает пакет.

Пока у storage нет условной записи, единый механизм — договор: все обработчики одной подписки берут `tl-<parent_user_service_id>`, пишут свой `lock_id`, не удаляют чужой и перед изменением лимита перечитывают и lock, и пользователя. Договор гонку не закрывает. Для Production нужна либо условная запись в storage, либо один последовательный исполнитель на подписку.

## 7. Блокирующие условия Production

Функцию нельзя включать, пока не закрыты все пункты:

1. `ACTIVATE` и `PROLONGATE` основного шаблона по-прежнему записывают каталожные 300 ГиБ и стирают оплаченный пакет. Этот шаблон умеет вернуть итог только на следующем своём запуске и проигрывает гонку продлению.
2. Постоянный `FAIL` повторяется без ограничения, пока сверка не ставит pause.
3. TTL, `lock_id`, `version` и `write_id` не заменяют CAS. Повторные чтения не закрывают гонку между подтверждающим GET и следующей записью. Продление основного шаблона этот ключ не берёт и может стереть пакет.
4. Событие `CREATE` нельзя вешать на группу серверов 6 без `template_id`: SSH иначе запустит серверный шаблон `remnawave` и создаст пользователя `us_<id дополнительной услуги>`.
5. Подписка, созданная в прошлом периоде, не получает пакет, пока `lastTrafficResetAt` не попадёт в текущее окно. Пустой `createdAt` в ответе панели тоже оставляет покупку закрытой.
6. vpnbot должен записывать `expected_amount` и `snapshot_mac` ключом сервера до заказа. Без этого шаблон отказывает. Пользователь может переписать собственный storage; подпись это обнаруживает, только если ключ ему недоступен.
7. `period_crossed` и потеря lock после уже выполненного PATCH оставляют панель изменённой без `APPLIED`. Пока сверка не разбирает эти записи, включать продажу нельзя.

Отдельно остаётся уже известное ограничение ядра: два одновременных `is_pay` могут увести баланс в минус. Этот этап ядро не меняет.

## 8. Развёртывание, которое этим этапом не выполняется

1. В SHM Admin открыть шаблоны и добавить шаблон с идентификатором `remnawave_traffic_addon`.
2. Вставить содержимое `templates/shm-remnawave-traffic-addon.template.sh`.
3. Не создавать событие и не заказывать услугу 17, пока не приняты блокирующие условия и vpnbot не пишет storage и `user_services.settings`.
4. Не привязывать категорию `traffic-add-vff` к группе 6 без `template_id`.
5. Не добавлять для этой категории события `ACTIVATE`, `BLOCK`, `PROLONGATE`, `REMOVE`, `CHANGED`. Успешный SSH записывает `server_id` в настройки экземпляра; следующее событие без собственного `template_id` ушло бы в основной шаблон `remnawave`.

Черновик события, которое сейчас создавать нельзя:

```json
{
  "kind": "UserService",
  "name": "create",
  "title": "vff traffic addon",
  "server_gid": 6,
  "settings": {
    "category": "traffic-add-vff",
    "template_id": "remnawave_traffic_addon"
  }
}
```

Группа 6 даёт шаблону адрес и токен Remnawave через `server.settings.remnawave.api` и `server.settings.remnawave.token`, а ключ снимка — через `server.settings.traffic_addon.snapshot_key`. Токен и ключ в лог не пишутся. Оба попадают в текст SSH-задачи так же, как токен уже попадает в основной шаблон: журнал spool не должен печатать тело скрипта.

## 9. Storage, TLS и временные файлы

Пользовательский маршрут `/shm/v1/storage/manage` читает, создаёт, заменяет и удаляет любую запись своего `user_id`, включая `ta-*` и `tl-*`. Отдельного серверного хранилища и запрета по имени ключа в штатном SHM нет. Чужие строки пользователь не видит. Описание услуги через пользовательский API меняет только текст description; полную замену `settings` экземпляра штатный пользовательский маршрут не даёт, административный — даёт.

Поэтому клиент может подменить объём, итог, ожидаемую сумму, финансовые идентификаторы, состояние и сам создать или удалить блокировку. Проверка `base + addon = applied` такую подмену не ловит. Принятая защита без изменения ядра — `snapshot_mac`. vpnbot подписывает неизменяемые поля ключом, которого нет в пользовательском storage. Шаблон закрывается, если ключа или верной подписи нет. Это не мешает пользователю удалить блокировку или испортить состояние: испорченное состояние без верной подписи на неизменяемых полях отклоняется, а терминальное состояние не реактивируется. Удаление ключа `ta-*` даёт `storage_missing` и не выдаёт трафик.

Скалярные значения SHM входят в шаблон через `toJson` и читаются `jq`. Команда внутри строки категории или идентификатора не выполняется. JSON настроек, каталога и списания передаётся в одинарных heredoc.

`curl` не использует `-k`. С хоста, где выполняется шаблон, цепочки `bill.portalbase.link` и `remna.vpn-for-friends.com` проверяются системным хранилищем CA. Если позже появится частный CA, запрос закроется ошибкой, пока сертификат не будет установлен. Это предпочтительнее отключения проверки. Основной шаблон по-прежнему вызывает `curl -skS`; этот этап его не меняет.

Временные ответы лежат в одном каталоге `mktemp -d` при `umask 077`. Обработчик `EXIT` сначала отпускает свой lock, затем удаляет каталог и при успехе, и при обрабатываемой ошибке. Тела ответов Remnawave и SHM в `/tmp` не остаются. `TRAFFIC_ADDON_CLOCK_FILE` — только тестовый шов. В Production переменная не задаётся, и пользователь SSH её не устанавливает.
